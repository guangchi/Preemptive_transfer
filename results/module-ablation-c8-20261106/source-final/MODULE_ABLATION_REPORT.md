# 三模块消融：提前发送、短中聚合、优先抢占

日期：2026-11-06。固定原交错 15 请求 workload、并发 15、100ms 到达间隔、prefix caching=false、batch-invariant=true；long C8，保护参数始终为 85% / 3 次 / 50ms。所有组均采用 UCX TCP TX/RX=128KB、WRITE 窗口 1、event fence、eager progress=0。

## 定义与对照

“分块”决定一次提交多少 KV；“流式/提前发送”决定何时提交。分块后的 KV 可以等整条 prompt 算完才提交，也可以每批计算完成就提交已就绪部分。这里的流式只指 KV 传输，不是客户端 SSE token 流。

- baseline：项目的整请求 NixlPushConnector 路径，不代表所有原生 NIXL 连接器或其所有传输策略。
- full：按 batch 提前释放 KV，long C8，短/中每请求每 batch 聚合，short 可越过未保护 long。
- no_stream：保留 full 生成的每批 chunk 边界，只把每请求 chunk 留到其 prompt-final 才统一释放。仍分块、仍可插队，不会把“关闭提前发送”改成“关闭分块”。
- no_aggregation：保持提前发送与抢占，短/中改回 C8，long C8 不变。对照使用当前块大小 8，不使用历史 C4。
- fifo：保持提前发送与短/中聚合，禁止 short 越过 long。85%/3/50ms 参数仍保留，不用把最大抢占次数设为 0 来间接关闭。

聚合是同一请求在一个 batch 内的新 KV 合并，不含把多个请求打包进一次 WRITE。五组各三次，轮换顺序，独立重启服务，使用同版 runtime。三模块开关纳入 P/D 配置握手与 environment 记录。新开关默认全开，完整方案默认行为不变。

## 如何解释贡献

每个模块的条件边际贡献 = 关闭该模块的指标 − full 的指标。正值表示开启模块节省时间，负值表示增加时间。它回答“另外两个模块都开着时，去掉这一项会怎样”，包括与其他模块的交互；不是独立的因果百分比分摊，不能把三项直接相加等于 baseline→full 的差值。本实验未声称用五组确定全部 2³ 交互或 Shapley 归因。

每轮 15 请求（8 short、3 medium、4 long），每请求输出 8 tokens。long 指 10,000-token 输入，不是长输出 decode。makespan 是首个客户端发送到最后一个响应结束，含到达间隔和排队，不含模型启动/固定等待/清理。类别 TTFT/E2E 为逐请求客户端时间。配对均按同轮同 workload；三轮是小样本，不据此宣称统计显著性。

### 主要贡献来自提前发送

关闭提前发送的三轮为 6.914581/6.675585/6.733831s，完整方案为 5.633888/5.658878/5.659629s，三轮配对均改善。12 个 long 的首 WRITE 都在关闭组 prompt 完成之后；完整组则在 prompt 完成前约 895～1023ms 就开始提交。两组每轮 chunk 几何均为 short 9、medium 5、long 316，总 330，说明差异来自释放时机及其引起的调度交互，而非改了应用 chunk 大小。

完整方案相对本轮 baseline 缩短 8.73%（6.191333→5.650798s）。如果保留分块协议/仲裁但取消提前发送，反而比 baseline 慢 0.583s。这支持“额外分块/协议/调度成本需要提前发送来抵消”的解释，但不把这 0.583s 全部视为纯分块成本。

### 聚合减少操作，但本负载未证明稳定加速

关闭聚合每轮为 short 8、medium 27、long 316，共 351 次；完整组为 short 9、medium 5、long 316，共 330 次，减少 21 次 WRITE（约 6%），未减少总 KV block 数。short 每请求通常仅 8 blocks，C8 本已接近一次提交；聚合的操作数收益主要落在三条 medium。完整方案中的一条 short 跨 batch 产生 2+6 blocks，而关闭聚合会等满 8，因此 short chunk 总数并非必然随聚合减少。

三轮聚合对整批的节省为 +27.424 / −5.726 / +7.919ms，均值 +9.872ms，约 0.174%；medium TTFT 均值只减少 3.785ms，方向也非逐轮一致。三轮小样本不支持稳定显著加速，不能把“操作数减少”当作同等比例的 makespan 收益。也没有验证跨请求打包或历史 C4 粒度的独立贡献。

### 抢占改善 short，long 的代价必须用 FIFO 对照

完整方案每轮发生 2 次 short 插队；FIFO 每轮 0 次。short TTFT 三轮配对分别降低 81.792/180.847/233.556ms，均值 165.398ms（相对 FIFO 约 6.53%）；整批三轮均改善，均值减少 129.857ms（约 2.25%）。medium 和未直接被抢占 long 的改变属于整个排队、接收和 decode 批处理的连带效应，不能全部说成直接抢占收益。

| long 请求 | full E2E 三轮均值(ms) | FIFO E2E 三轮均值(ms) | full − FIFO(ms)，正值为代价 |
| --- | ---: | ---: | ---: |
| interleaved15-01-long | 1856.834 | 1723.932 | +132.903 |
| interleaved15-05-long | 2535.522 | 2571.777 | -36.255 |
| interleaved15-07-long | 3412.647 | 3525.197 | -112.551 |
| interleaved15-11-long | 4357.298 | 4402.361 | -45.064 |

long-01 三轮均受损，分别 +162.787/+127.551/+108.370ms，均值 +132.903ms，符合被插队的取舍。long-11 也发生插队，但三轮 full−FIFO 为 +49.212/−79.942/−104.461ms，方向不同。long 类整体 full 比 FIFO 平均快 15.242ms，也不是逐轮一致：full−FIFO 为 +58.133/−31.427/−72.431ms。不能声称抢占必然改善 long，或强行要求所有 long 都变慢。不同调度会改变后续排队与 decode batch；此对照测的是整个调度策略效果，不是固定其他一切后的单次插队纯等待。

## 验收与限制

15 个服务组、225/225 请求的 token ID 和文本 hash 匹配直接推理参考，所有 block 覆盖与序号无缺失/重叠。配置开关、UCX 参数、event、安全窗口与保护参数逐组一致性检查通过；FIFO 零插队、no_stream 不提前传输、全组 long C8 检查通过。完整方案 source 与消融使用同版 runtime，实验过程中 10 个 runtime 文件 hash 未变。回归为 84 passed、14 条 Torch 弃用警告。

含启动、固定等待、trace 与清理的脚本总时间 baseline/full 为 80.264/81.254s，本轮 full 数值更长。该指标主要由服务启动波动构成，不当作 KV 调度速度；workload makespan 单独记录。

逐轮原始差值见 `confirmation/ablation-results.json`，独立开关与轨迹审计见 `module-trace-audit.json`。本轮是关闭单项的条件贡献，未做全因子组合；三项存在交互，不提供加和为 100% 的贡献比例。
