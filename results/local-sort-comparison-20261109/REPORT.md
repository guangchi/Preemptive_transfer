# 密集与主实验：baseline、旧方案、新完整方案比较

2026-11-09。仅测试 250ms 和 500ms，不测试分散场景。每种配置 3 次正式重复，共 18 次正式实验；每次服务启动对两种场景各预热一次，预热不计入结果。

## 负载与控制变量

原测试集 SHA256：`714990980c49534e539a125612ce1c8d36c68ac75a559e4bce93dabcb7ee9e14`。15 条请求、8 short / 3 medium / 4 long，prompt 长度分别为 128 / 1107 / 10000 tokens，每条生成 8 tokens。保持原文件顺序，3 批各 5 条，批内间隔 0ms，并发 15。

| 场景 | 三批计划提交时间 | 批内原始请求组成 |
| --- | --- | --- |
| 密集 250ms | 0、250、500ms | 短长短中短 / 长短长短中 / 短长短中短 |
| 主实验 500ms | 0、500、1000ms | 同上 |

客户端不预排序；新方案在 P 侧 20ms 固定窗口内按实际 prompt token 数稳定排序。三轮实际提交时刻相对计划最大偏差约 12.70ms。窗口以 P 实际接纳时刻为准，TTFT 包含窗口等待。

两张 RTX 4090：P=GPU0，D=GPU1，TP=PP=1，Llama-3.1-8B-Instruct，vLLM 0.32.0，prefix cache 关闭，batch invariant 开启，计算预算每 batch 2048 tokens，NIXL/UCX TCP loopback，两端 TX/RX=128KB。

baseline 沿用此前实验口径：`NixlPushConnector`，`short_request_preemptive_transfer=false`，整请求 KV 发送。此次没有替换成另一套官方 connector。旧方案开启原完整传输机制；新方案在旧方案上只增加 P 局部排序。旧/新方案均使用 batch 提前发送、短中按 batch 聚合、long C8、85%/3 次/50ms、event fence、单 WRITE 槽。D 使用原调度器。

运行顺序轮换：第 1 轮 baseline→旧→新，第 2 轮旧→新→baseline，第 3 轮新→baseline→旧。轮次内两个负载交替顺序：250→500、500→250、250→500。

## 窗口、抢占与原因

| 场景 | 方案 | 三轮抢占次数 | 其中跨批次数 | 新方案各轮窗口大小 |
| --- | --- | --- | --- | --- |
| 250ms | baseline 整请求传输 | [0, 0, 0] | [0, 0, 0] | — |
| 250ms | 旧方案（无排序） | [3, 1, 0] | [0, 0, 0] | — |
| 250ms | 新完整方案（排序开启） | [0, 0, 2] | [0, 0, 2] | [[5, 5, 5], [5, 5, 5], [2, 3, 5, 5]] |
| 500ms | baseline 整请求传输 | [0, 0, 0] | [0, 0, 0] | — |
| 500ms | 旧方案（无排序） | [0, 2, 2] | [0, 0, 0] | — |
| 500ms | 新完整方案（排序开启） | [0, 3, 0] | [0, 3, 0] | [[5, 5, 5], [3, 2, 5, 5], [5, 5, 5]] |

6 次新方案正式实验中，4 次形成 `[5,5,5]`；主实验第 2 轮为 `[3,2,5,5]`，密集第 3 轮为 `[2,3,5,5]`。两次拆窗都只发生在原始首批内部，没有不同原始批次混排。原因为 P 接纳间隔超过 20ms；保留实测结果，未为凑足五条而扩大窗口或补选更有利轮次。所有窗口均满足 token 数升序及同长度稳定顺序，窗口先后释放。实际窗口等待最大约 232.84ms，释放仍受下一次引擎调度时机影响。

新方案 250ms 三轮共 2 次跨批传输抢占，500ms 共 3 次；其中多轮没有抢占，但仍取得更低 short TTFT。因此本轮排序新增收益主要体现在 P 接纳与计算预算分配，不能全部归于传输抢占。排序让同一窗口的短中请求先获得计算机会，从而更早产生可发送 KV；具体调度与执行顺序保存在 P 日志。

新增排序的代价是 long 相对旧方案平均 TTFT 增加约 3.71% / 4.32%，E2E 增加约 3.33% / 3.74%，但仍优于 baseline。旧方案虽降低总时间，却不保证每个场景的 short TTFT 都优于 baseline：500ms 场景旧方案 short 均值为 2588ms，baseline 为 2440ms，且重复波动较大；新方案均值降至 1566ms。

不同窗口之间保留先后关系，已运行 long 不被 P 计算调度抢占；后批短请求仍可能等待。因此第三批短请求明显比首批慢。这里的抢占计数均为 KV 传输 chunk 边界的抢占，不代表 GPU 计算被打断。

## 正确性与数据

- 正式 270/270、加预热 540/540 请求成功，每条输入 token 数正确、输出 8 tokens；所有逐请求 token IDs 均匹配此前独立参考结果。
- 18 次正式轮均通过完整 P/D 执行时间线核验。旧/新方案另通过 chunk 生命周期完整性核验，180/180 条 D 首次模型提交发生在 KV 收齐之后。baseline 沿用原整请求日志，缺少相同 chunk 生命周期打点，因此不虚构对应的逐 chunk 接收时刻。
- baseline 没有局部排序和传输抢占；旧方案无局部排序；新方案每条请求都出现且仅出现一次窗口入队记录。
- 所有实验均已退出，GPU0/1 显存恢复约 9MiB。代码回归 93 passed、14 条已有 Torch 弃用提示。
